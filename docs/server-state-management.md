# 서버 상태 관리: TanStack Query 도입

작성일: 2026-11-16 · 기준: 현재 소스와 이번 리팩토링에서 논의한 내용

이 문서는 블로그에 TanStack Query(이하 React Query)를 도입한 배경과 현재 구현 방식을 기록한다. 대안 비교는 프로젝트 요구에 대한 판단이며, 성능이나 라이브러리 크기를 측정한 결과는 아니다.

## 배경과 문제

처음에는 카테고리·태그처럼 서버에서 가져온 데이터도 `useEffect`와 `useState`로 각 화면에서 따로 관리했다. 요청마다 데이터, 로딩, 오류 상태를 만들고 변경 후에는 목록을 다시 불러오는 코드를 연결해야 했다. 같은 태그 목록이 여러 화면에 있을 때 각 상태를 갱신하는 책임도 흩어져 있었다.

또한 글 작성 관련 로직을 하나의 큰 커스텀 훅에 모으면서 페이지에서 어떤 상태와 동작을 사용하는지 파악하기 어려웠다. 모든 상태에 라이브러리가 필요한 것은 아니지만, **서버에서 받아 여러 곳에서 쓰거나 변경 후 다시 확인해야 하는 데이터**에는 공통 관리 방식이 필요했다.

## 대안과 선택

| 대안                            | 장점과 고려할 점                                                                                                             | 이번 판단                                                                |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| React state와 `useEffect` 유지  | 의존성이 없고 단순한 단일 요청에는 충분하다. 공유 캐시, 중복 요청, 재조회와 오류 처리는 직접 관리해야 한다.                  | 화면에 한정된 상태는 유지하고 서버 데이터 관리에는 공통 도구를 사용한다. |
| SWR                             | 간결한 API로 조회, 캐시와 갱신을 다룰 수 있고, 이미 프로젝트에 설치돼 있었다. 변경과 캐시 갱신도 처리할 수 있다.             | 현재 규모에 충분한 대안이지만 이번 작업에서는 React Query로 통일했다.    |
| TanStack Query                  | 조회뿐 아니라 생성·수정·삭제의 진행 상태와 관련 캐시 갱신을 명시적으로 관리할 수 있다. Provider 설정과 추가 학습이 필요하다. | 게시글·카테고리·태그의 변경 흐름을 정리하고 향후 확장하기 위해 선택했다. |
| Redux·Zustand 등 범용 상태 관리 | 여러 화면의 클라이언트 상태를 공유하는 경우 유용하다. 서버 데이터의 재조회와 동기화 문제를 별도로 설계해야 한다.             | 현재 테마, 모달, 입력값을 위해 새 전역 상태 도구를 추가하지 않았다.      |

SWR이 기능상 부족해서 선택하지 않은 것은 아니다. 두 도구를 함께 사용하면 서버 상태 관리 방식이 나뉘므로 새 구현은 React Query를 기준으로 한다. `swr` 패키지는 현재 의존성에 남아 있으며 제거 작업은 이번 범위에 포함하지 않았다.

## 상태별 책임

| 상태                      | 관리 위치                        | 예시                                          |
| ------------------------- | -------------------------------- | --------------------------------------------- |
| 서버 데이터와 요청 상태   | `src/queries`의 React Query 훅   | 태그 목록, 수정할 게시글, 생성·삭제 진행 상태 |
| API 통신                  | `src/lib/services`               | 요청 URL, 본문, 응답과 오류 처리              |
| 화면에 한정된 상태        | 페이지·컴포넌트 또는 `src/hooks` | 에디터 입력, 선택한 태그, 모달 열림           |
| 화면 간 공통 UI 상태      | Context                          | 테마                                          |
| 공유 가능한 필터 상태     | URL 검색 파라미터                | 선택한 태그와 페이지 번호                     |
| 공개 페이지의 초기 데이터 | 서버 컴포넌트와 `src/lib/data`   | 공개 게시글 및 서버에서 읽은 초기 목록        |

React Query가 서버의 DB를 직접 읽는 것은 아니다. 클라이언트 쿼리 훅은 서비스 함수를 통해 API Route를 호출하고, 결과를 브라우저의 쿼리 캐시에 저장한다. 공개 게시글처럼 서버 컴포넌트에서 DB를 직접 조회하는 경로도 유지한다.

## 현재 구조와 규칙

```text
src/
├── queries/
│   ├── category.ts  # 카테고리 쿼리 키, 조회와 변경
│   ├── post.ts      # 게시글 쿼리 키, 조회와 변경
│   ├── tag.ts       # 태그 쿼리 키, 조회와 변경
│   └── visitor.ts   # 방문자 통계 조회와 방문 기록
├── hooks/           # 모달, 메뉴 등 화면 동작과 요청 흐름 조합
├── lib/services/    # 클라이언트 API 요청 함수
└── lib/data/        # 서버에서 사용하는 데이터 조회 함수
```

- 쿼리 키는 관련 훅이 있는 도메인 파일에 둔다. 예를 들어 `tagQueryKeys.all`을 조회와 갱신 양쪽에서 사용한다.
- 쿼리 훅은 React Query 결과를 반환하고, 사용하는 곳에서 `data`, `isLoading`, `isError`, `mutateAsync`, `isPending` 등을 구조 분해해 필요한 이름으로 사용한다.
- 서버 변경은 `useMutation`에서 처리한다. 서비스가 실패를 반환값으로 알리는 경우 mutation에서 오류로 변환해 실패 상태를 표현한다.
- 모달의 선택값과 입력 검증은 로컬 상태로 관리한다. 서버 오류는 mutation 상태를 사용하고, 모달을 닫거나 선택을 바꾸면 필요한 경우 `reset()`으로 이전 오류를 지운다.
- 화면 로직을 무조건 훅으로 옮기지 않는다. 글 작성 화면의 큰 `usePostEditor`와 데이터 조합 훅을 제거해 페이지에서 흐름을 볼 수 있게 했고, 책임이 명확하거나 재사용이 필요한 경우에 훅을 분리한다.

전역 Provider는 쿼리의 기본 `staleTime`을 60초, 실패 재시도를 1회로 설정한다. 각 쿼리에서 필요한 설정을 덮어쓸 수 있다. mutation의 재시도나 캐시 무효화도 해당 동작의 성격을 보고 결정한다.

## 기능별 적용

### 카테고리와 태그

카테고리와 태그의 조회·생성·삭제를 도메인별 쿼리 훅으로 관리한다. 카테고리 삭제는 게시글 쿼리도 무효화하고, 태그 생성·삭제는 태그 목록을 갱신한다. 태그 삭제 시에는 캐시에서 삭제된 태그를 먼저 제거하고 태그와 게시글 쿼리를 무효화한다.

카테고리와 태그 화면은 서버에서 받은 목록을 쿼리의 초기 데이터로 사용할 수 있다. 태그 페이지는 별도의 목록 state를 유지하는 대신 쿼리 캐시를 구독하며, 삭제 후에는 서버 화면도 `router.refresh()`로 갱신한다. 초기 데이터는 해당 키의 캐시가 아직 없을 때 사용된다. 서버 props와 이미 존재하는 클라이언트 캐시가 자동으로 양방향 동기화된다는 의미는 아니다.

### 게시글

게시글 생성·수정·삭제 성공 후 게시글과 태그 쿼리를 무효화한다. 수정 화면의 게시글 쿼리는 `staleTime: 0`, 마운트 시 재조회, 포커스 재조회 비활성화를 설정한다. 수정 화면은 새 조회가 끝난 뒤 에디터를 초기화하고, 이후 같은 글의 재조회가 작성 중인 입력을 덮어쓰지 않도록 한다.

이는 **수정 화면을 열 때의 최신성**을 위한 조치다. 편집을 시작한 뒤 다른 곳에서 같은 글을 수정하는 경우의 충돌 감지나 저장 시 버전 검사는 아직 구현하지 않았다.

### 방문자

방문 기록 POST는 데이터 변경이므로 mutation으로 실행하고 자동 재시도하지 않는다. 같은 QueryClient에서 동시에 진행 중인 기록 요청은 공유한다. 기록 성공 시 반환된 통계를 캐시에 저장하고, 실패 시에는 통계 GET을 별도로 시도한다. 통계 조회까지 실패하면 오류를 표시한다.

서버는 방문 쿠키로 집계 여부를 판단한다. 진행 중인 요청 공유와 쿠키는 중복 집계 가능성을 줄이기 위한 현재 방식이며, 모든 동시 요청이나 네트워크 실패 상황에서 정확히 한 번만 집계된다는 보장은 아니다.

## 캐시와 서버 렌더링의 경계

React Query 캐시는 브라우저의 QueryClient가 관리한다. `invalidateQueries`는 해당 쿼리를 오래된 상태로 표시하고 활성 쿼리를 기본 설정에 따라 다시 조회하지만, **서버 컴포넌트를 자동으로 다시 렌더링하지는 않는다.** 서버 렌더링 결과도 갱신해야 하는 변경에서는 화면의 `router.refresh()`와 서버 측 캐시 정책을 함께 검토한다.

서버 컴포넌트에서 직접 호출하는 데이터 함수와 서버 액션도 구분한다. 현재 공개 페이지의 서버 데이터 조회는 Prisma를 호출하는 서버 측 함수다. React의 `cache()`를 쓰는 조회는 서버 렌더링에서 작업을 공유하는 용도이며 브라우저의 React Query 캐시와 별개다.

## 기대 효과와 남은 확인

이번 구조로 쿼리 키, 요청 상태와 변경 후 갱신 대상이 한곳에 드러나므로 같은 데이터를 사용하는 화면을 추가하거나 수정할 때 확인할 지점이 명확해진다. 로딩·오류와 캐시 갱신을 각 화면에서 중복 구현할 필요도 줄어든다. 이는 유지보수 관점에서 기대하는 효과이며, 네트워크 요청 수나 속도 개선을 측정한 결과는 아니다.

쿼리 무효화, 모달 오류·초기화, 태그 캐시와 글 작성·수정 흐름은 Jest 테스트로 확인한다. 실제 브라우저에서 로그인한 뒤 게시글 작성·수정·삭제, 태그·카테고리 변경과 페이지 이동을 점검하는 작업은 별도로 필요하다. 기존 전체 포맷 검사 경고와 린트 경고도 이번 서버 상태 도입만으로 모두 해결된 것은 아니다.

새 기능을 추가할 때는 다음을 확인한다.

1. 데이터가 서버 상태인지, 화면 입력·선택 상태인지 구분한다.
2. 서버 상태라면 도메인 쿼리 파일에 키와 조회·변경 훅을 두고, 사용처에서는 필요한 상태를 구조 분해한다.
3. 변경 성공 시 영향을 받는 클라이언트 쿼리와 서버 렌더링 화면을 각각 확인한다.
4. 실패·재시도와 입력값 보존을 검토하고, 중요한 사용자 흐름을 테스트한다.
