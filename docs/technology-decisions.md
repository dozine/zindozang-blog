# 기술 스택과 선택 근거

작성일: 2026-10-30 · 기준: 현재 소스, package.json, 이전 현황 점검

## 1. 이 프로젝트에서 기술을 선택하는 기준

Zindozang은 관리자가 직접 글을 작성하고 운영하는 개인 블로그다. 읽기 화면뿐 아니라 로그인, 작성 도구, 이미지 업로드, 공개 상태 관리까지 한 사람이 유지해야 한다.

이 조건에서는 **기능 구현 시간, 운영해야 하는 서비스 수, 장애를 추적하는 비용, 장기간 방치 후 다시 이해하는 비용**을 함께 줄이는 구성이 유리하다. 최대 확장성보다 일관된 개발 흐름과 관리형 서비스의 활용을 우선한다.

이 문서의 선택 근거는 코드에서 확인한 역할과 현재 요구사항을 바탕으로 재구성한 설계 설명이다. 당시 개발자의 실제 검토 기록이나 모든 대안의 실험 결과를 의미하지 않는다. 성능·비용을 측정하지 않은 상태에서 “가장 빠르다”, “가장 저렴하다”, “유일한 최적해”라고 주장하지 않는다. 대안 비교와 유지·전환 권고는 이 프로젝트에 대한 판단이다.

## 3. Next.js와 React — 화면과 서버를 한 프로젝트에서 관리

### 선택 근거

블로그에는 검색·공유를 고려한 공개 페이지와 로그인 후 사용하는 작성 화면이 함께 있다. Next.js 안에서 페이지, 서버 데이터 조회, API를 구현하면 별도 백엔드 저장소·배포·인증 연결을 관리하는 부담을 줄일 수 있다. React 컴포넌트와 훅을 공유하면서 읽기와 쓰기의 요구를 구분할 수 있다는 점이 이 프로젝트에 적합하다.

현재 `app/(blog)/blog/page.tsx`와 `lib/data/post.ts`는 서버 조회를, 작성 화면과 API Route는 편집·저장을 담당한다. Next.js는 서버 컴포넌트와 클라이언트 상호작용을 조합하도록 지원한다. [공식 설명](https://nextjs.org/docs/app/getting-started/server-and-client-components)

### 대안과 비교

| 대안 | 이 프로젝트에서 유리할 조건 | 현재 선택의 이유 |
| --- | --- | --- |
| Vite + React + 별도 API | 프론트·백엔드의 배포/책임을 나눌 필요가 큼 | 혼자 관리할 서버와 연결 지점을 줄일 수 있음 |
| Astro + Markdown/MDX | Git에서 글을 쓰고 정적 콘텐츠 제공이 주목적 | 현재는 브라우저 작성·DB 초안 관리가 있어 Next 흐름을 유지하기 쉬움 |
| 외부 CMS + 프론트 | 작성 기능을 직접 개발할 필요가 적음 | 집필 도구와 운영 흐름을 직접 제어하는 요구를 구현할 수 있음 |

### 한계와 판단

Next.js를 사용한다고 자동으로 빠르거나 SEO가 완성되지는 않는다. 현재 테마 Provider가 마운트 전 전체 화면을 숨기는 문제부터 수정해야 한다. 서버 조회, 캐시, 메타데이터, 초기 HTML을 실제로 검증하는 것이 프레임워크 교체보다 우선이다.

현재 기능을 유지하는 한 교체 필요성은 낮다. 반대로 앞으로 “코드 저장소에서 글을 쓰는 단순 아카이브”로 목표를 바꾼다면 DB·인증·작성 화면을 줄이고 정적 구성을 검토할 수 있다.

## 4. TypeScript — 혼자 수정할 때 놓치는 연결 오류 줄이기

페이지·훅·API·DB가 같은 도메인 데이터를 다루므로 타입은 변경 영향 범위를 확인하는 도구다. 이미지와 태그 구조가 바뀔 때 호출부의 영향을 드러낼 수 있어, 오랜 공백 후 개발을 재개하는 상황에도 유용하다.

JavaScript + JSDoc보다 타입을 코드 전반에 일관되게 적용하기 쉬운 선택으로 설명할 수 있다. 다만 현재 `strict: false`와 `any`가 있어 보호 범위가 제한적이다. “TypeScript로 런타임 오류를 방지했다”보다 “정적 검사를 도입했고 계약을 강화하는 중”이라는 설명이 정확하다.

TypeScript 타입은 외부 요청을 검증하지 않는다. 우선 API 경계에 Zod 같은 런타임 스키마 또는 일관된 검증 함수를 검토하고, 응답 DTO와 nullable 데이터부터 엄격하게 만든다. 스키마 라이브러리 도입은 제안이며 현재 구현된 기술이 아니다.

## 5. CSS Modules와 React 기본 상태 — 필요한 범위만 관리

화면별 CSS를 컴포넌트와 가까이 두고 전역 충돌을 줄일 수 있다. 현재 규모에서는 별도 스타일 시스템의 규칙과 설정을 추가하는 것보다 직접적인 CSS가 이해·수정하기 쉽다. Tailwind는 반복 유틸리티와 디자인 규칙을 공유할 때 좋은 대안이고, UI 라이브러리는 복잡한 접근성 패턴을 빠르게 확보할 때 유리하지만 현재 화면을 전면 재작성할 이유는 부족하다.

상태도 글 편집·모달은 로컬 state, 테마는 Context, 필터는 URL에 두는 방향이 적절하다. Redux나 Zustand가 없어도 요구를 충족한다. URL 필터는 공유·뒤로 가기와 연결되는 장점이 있다.

여러 화면 사이에서 같은 원격 데이터를 반복 갱신하며 동기화 오류가 늘면 TanStack Query나 SWR를 검토한다. 현재 태그 setter가 빈 함수인 문제는 라이브러리 도입 전에 상태 연결부터 고쳐야 한다. 공통 색상·여백은 CSS 변수로 정리하고, 메뉴·모달의 키보드 접근성은 별도로 개선한다.

## 6. Prisma와 MongoDB — 개발 편의와 데이터 모델의 절충

### 선택 근거

Prisma는 모델과 데이터 접근 API를 정리해 UI부터 DB까지 혼자 다룰 때 쿼리 코드의 형태를 일관되게 유지하는 데 도움이 된다. 글·태그 관계와 트랜잭션을 명시한 현재 코드에도 이 장점이 보인다. MongoDB는 문서 형태로 콘텐츠를 다루는 데 자연스러운 면이 있고, 기존에 구축된 연결과 데이터가 있다면 유지 비용을 줄이는 선택이다. README에는 Atlas 사용이 기재돼 있으나 운영 계정 설정까지 확인한 것은 아니다.

“블로그는 문서니까 MongoDB가 가장 적합하다”는 설명은 충분하지 않다. 현재 본문은 문자열이고, 글·태그·분류·사용자·세션은 관계 중심 모델이다. 관계형 DB에서도 그대로 표현할 수 있다.

### 대안과 판단

| 대안 | 장점으로 기대할 부분 | 이 프로젝트의 전환 비용 |
| --- | --- | --- |
| PostgreSQL + Prisma | 관계 제약, SQL 집계, 명시적인 스키마 마이그레이션 | 데이터·ID·관계·인증 데이터 이전과 쿼리 검증 |
| SQLite 계열 | 작은 서비스의 단순한 저장 모델 | 현재 호스팅의 저장 지속성·동시 쓰기·연결 방식을 다시 설계 |
| MongoDB native driver / Mongoose | MongoDB 특화 기능을 직접 제어 | 기존 Prisma 모델과 쿼리 재작성, 타입·검증 정책 재구성 |

**지금 운영 데이터를 옮길 만큼의 근거는 부족하다.** 먼저 권한, 오류 처리, 인덱스를 보완한다. 다중 작성자·복잡한 통계·관계 제약·데이터 변경 이력이 중요해진다면 PostgreSQL을 우선 비교할 만하다. 새로 같은 관계 모델을 만든다는 조건이라면 PostgreSQL 쪽에 더 무게를 둘 수 있다. 이는 요구사항에 대한 판단이며 성능 벤치마크 결과는 아니다.

Prisma의 MongoDB 연결은 관계형 DB와 제약이 다르며 Prisma Migrate 대신 `db push`를 사용한다. 트랜잭션에는 replica set 구성이 필요하다. **점검일의 공식 안내는 MongoDB 사용 시 Prisma 6.19 사용을 권고하고 v7 지원은 준비 중이라고 설명한다.** 현재 6.19.2 설치 상태에서 메이저 버전을 일괄 올리면 안 된다. 업그레이드 직전에 지원 상황을 다시 확인한다. [Prisma MongoDB 공식 문서](https://www.prisma.io/docs/orm/overview/databases/mongodb)

ORM이 있다고 DB 변경·백업·복구·관계 무결성 운영이 모두 해결되는 것은 아니다. 스키마 변경 절차와 복구 방법을 별도로 남긴다.

## 7. NextAuth — 비밀번호 인증을 직접 운영하는 범위 줄이기

관리자 한 명의 로그인에 회원가입, 비밀번호 재설정, 이메일 발송을 모두 구현하는 비용은 크다. Google/GitHub OAuth와 세션을 NextAuth에 맡기고 `MYEMAIL`로 접근 대상을 제한하는 방식은 서비스 목적에 비해 구현 범위를 작게 유지한다. Prisma Adapter를 통해 기존 DB와 인증 데이터를 연결한다.

직접 OAuth/세션을 구현하면 제어 범위가 커지지만 관리해야 할 보안 코드가 늘어난다. Clerk 같은 관리형 인증은 운영을 맡길 수 있으나 추가 서비스와 데이터·요금 정책을 검토해야 한다. Firebase Auth를 쓰면 Storage 인증과 맞추는 이점이 있을 수 있지만 현재 세션과 어댑터를 바꾸는 비용이 있다.

현재 우선순위는 인증 도구 교체가 아니라 **각 API에서의 관리자 권한 검사**다. 로그인 제한은 API 권한 검사를 대신하지 않는다. 서버에서는 현재의 `getAuthSession`처럼 서버 세션을 조회하는 흐름을 유지한다. [NextAuth v4 서버 세션 문서](https://next-auth.js.org/configuration/nextjs)

인증 라이브러리의 메이저 변경은 provider callback, cookie/session, DB adapter, preview 도메인, 기존 로그인 회귀 검증을 묶어 별도 작업으로 진행한다. 최신 이름이나 버전만을 이유로 즉시 전환하지 않는다.

## 8. Firebase Storage — 앱 서버의 파일 관리 부담 줄이기

이미지를 애플리케이션 서버의 로컬 디스크에 저장하지 않고 외부 Storage에 저장하면 파일 보관과 앱 배포를 분리할 수 있다. 현재 Firebase SDK로 브라우저에서 업로드하고 URL을 DB에 저장하는 방식은 업로드 진행률을 구현하기도 쉽다.

S3 계열 Object Storage + 서명 업로드 URL은 현재 NextAuth 권한을 서버에서 검사한 뒤 업로드를 허용하는 대안이다. 이미지 변환과 전달까지 맡기고 싶으면 이미지 전문 서비스도 비교할 수 있다. 실제 비용은 저장량·다운로드·변환·리전·플랜 조건을 계산해야 하며 현재 서비스가 무료이거나 가장 저렴하다고 가정하지 않는다.

**현재 조합의 가장 큰 과제는 NextAuth와 Firebase의 인증 경계다.** NextAuth 로그인 상태는 Firebase Storage Rules에 자동 전달되지 않는다. Storage 권한은 Rules와 인증 연동을 포함해 따로 설계해야 한다. [Firebase Storage 보안 공식 문서](https://firebase.google.com/docs/storage/security)

Firebase 인증 토큰을 연동하거나 서버에서 통제하는 업로드 방식을 검토한다. 현재 Rules가 공개인지 여부는 코드만으로 판정하지 않았다. 이 연결이 지나치게 복잡하다면 같은 세션으로 서명 URL을 발급하는 Storage 구성이 1인 운영에 더 단순할 수 있다.

저장소 교체 전에 썸네일과 본문 이미지 목록을 분리하고, 세 크기 파생 파일을 어디에 쓰고 언제 삭제할지 정한다. `next/image` 최적화까지 사용하므로 브라우저 리사이즈와의 역할도 나눠 불필요한 업로드·보관을 줄인다.

## 9. Markdown — 글의 수명과 에디터의 수명 분리

기술 글은 제목, 목록, 링크, 표, 코드가 중심이다. Markdown은 저장 형식이 비교적 단순하고 다른 도구로 가져가기 쉬워 에디터 구현에 대한 의존을 낮출 수 있다. 작성 UI와 공개 렌더러를 분리하고 작성 에디터만 동적 로딩한 현재 방향은 유지할 가치가 있다.

| 대안 | 맞는 요구 | 현재 Markdown을 유지하는 이유 |
| --- | --- | --- |
| Quill/Tiptap 등 리치 텍스트 | 비개발자 집필, 블록 편집·정교한 서식 | 기술 글 위주라 복잡한 편집 모델의 필요가 작음 |
| Git 기반 MDX | 코드 리뷰로 글 관리, 문서 안 React 표현 | 브라우저 작성·DB 저장 흐름을 유지하려는 현재 목표 |
| 외부 CMS | 편집 워크플로우를 외부 도구에 위임 | 현재 작성 경험을 직접 조정할 수 있음 |

Markdown이라고 자동으로 번들이 작거나 안전한 것은 아니다. 현재 `rehypeRaw`로 HTML 이미지 그리드를 허용하므로 허용 태그·속성 정책과 sanitizer를 검토한다. 필요한 HTML을 보존하며 실제 공격 문자열을 검증해야 한다. [react-markdown 보안 안내](https://github.com/remarkjs/react-markdown#security)

Prism 기반 코드 강조는 기존 구현을 유지하면서 언어·테마 import 비용을 측정한다. 서버 중심 강조 도구로의 전환은 공개 화면 JavaScript 비용이 실제 병목일 때 비교한다. Quill 잔재와 중복 파서부터 정리하는 편이 우선이다.

## 10. Utterances — 댓글 운영을 별도 구현하지 않기

댓글을 직접 만들면 작성자 인증, 삭제·신고·스팸 관리와 데이터 운영까지 필요하다. Utterances는 GitHub Issues를 댓글 저장소로 사용하므로 개발자 중심 독자층에서는 이 범위를 줄일 수 있다. 댓글 작성에 GitHub 인증이 필요하다는 진입 장벽도 있다. [Utterances 공식 설명](https://utteranc.es/)

GitHub Discussions 기반 giscus나 자체 댓글이 대안이다. 독자층·관리 방식에 문제가 없다면 교체 우선순위는 낮다. 먼저 테마 동기화와 글 이동 시 초기화·정리 동작을 고친다. 글 slug를 댓글 연결 키로 사용하므로 URL을 바꾸는 경우 기존 댓글의 연결 정책도 정한다.

## 11. Vercel과 GitHub Actions — 배포를 반복 가능한 작업으로 만들기

한 사람이 서버 설치·프로세스 관리·배포까지 직접 운영하는 시간을 줄이기 위해 Next.js 호스팅을 관리형 플랫폼에 맡기는 선택은 합리적이다. GitHub Actions는 소스 변경에 대해 검증 명령과 배포 조건을 남길 수 있다.

현재 workflow에는 dev preview/main production 배포 경로가 있다. Vercel 자체 Git 연동도 배포를 지원하므로 실제 계정에서 두 경로가 중복 실행되는지 확인하고 주 배포 경로를 하나로 정한다. [Vercel Git 배포 문서](https://vercel.com/docs/git)

VPS/Docker는 운영 제어가 필요할 때, 다른 관리형 플랫폼은 기능·요금·리전 요구가 달라질 때 비교한다. 현재는 이전보다 실패 감지와 복구 절차를 먼저 갖추는 것이 효율적이다. preview와 production의 DB/Storage·OAuth 환경도 분리 여부를 확인한다.

Vercel Analytics, GA, 자체 방문자는 측정 목적이 다르다. 핵심 목적을 정의하지 않으면 계측 코드만 늘어난다. 단순 방문 추세가 목적이면 중복 집계를 줄이고, GA를 유지한다면 현재 꺼 둔 자동 page_view를 대체할 전송 경로를 확인한다.

## 12. 테스트 도구 — 도구 수보다 실행되는 검증

Jest와 Testing Library는 단위·컴포넌트 테스트 기반, Storybook은 UI 상태 확인 기반, Vitest와 Playwright 설정은 스토리 브라우저 검증 기반이다. 현재 Jest 테스트는 0개이며 Storybook 테스트는 CI에서 실행하지 않는다. 따라서 “테스트 자동화를 완료했다”는 표현은 현재 상태와 맞지 않는다.

1인 개발에서는 다음 범위를 우선 확보하는 것이 좋다.

1. 비로그인 변경 요청과 비공개 글 노출을 차단하는 서버 테스트.
2. 태그 생성·선택·필터링과 저장 응답 계약 검증.
3. 로그인 후 초안 저장→수정→공개→조회하는 핵심 브라우저 흐름.

당장은 기존 Jest를 활용해 중요한 테스트를 만든다. 이후 Storybook/Vitest와 함께 유지하는 설정 비용이 실제로 크다면 일반 테스트를 Vitest로 통일하는 방안을 검토한다. 테스트가 생기기도 전에 러너를 바꾸는 것은 우선순위가 낮다. 브라우저 테스트의 Next 서버 모듈·인증·DB 실행 환경도 별도로 고려한다.

린트는 Next.js 16에서 `next lint`가 제거됐으므로 ESLint CLI로 바꾸고 별도 CI 단계로 실행해야 한다. build가 lint까지 수행한다고 가정하면 안 된다. [Next.js 16 업그레이드 문서](https://nextjs.org/docs/app/guides/upgrading/version-16)

## 13. 보충 운영 지침

### 환경변수는 역할과 공개 범위를 함께 기록

실제 `.env` 값을 문서에 복사하지 않는다. 아래 이름은 소스 참조 기준이며 값은 환경별로 설정한다.

| 구분 | 변수 | 관리 기준 |
| --- | --- | --- |
| DB | `DATABASE_URL` | 서버 전용 비밀 값, preview/운영 대상 구분 |
| 인증 | `GOOGLE_ID`, `GOOGLE_SECRET`, `GITHUB_ID`, `GITHUB_SECRET` | provider 설정과 callback 도메인 연결, secret은 서버 전용 |
| 관리자 | `MYEMAIL` | 접근 정책 값, 누락 시 명확히 실패하도록 검증 |
| NextAuth 환경 | `NEXTAUTH_URL`, `NEXTAUTH_SECRET` | v4 배포 설정 확인 대상; 실제 환경별 요구는 provider/배포 설정과 검증 |
| 브라우저 Firebase 설정 | `NEXT_PUBLIC_FIREBASE`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`, `NEXT_PUBLIC_MESSAGING_SENDER_ID` | 브라우저에 포함되는 설정이며 저장소 접근 권한을 대신하지 않음 |
| Firebase app 식별자 | 현재 `FIREBASE_APP_ID` 참조 | 클라이언트 import 코드에서 사용하므로 public 변수명·전달 방식 재검토. 앱 식별자를 관리자 비밀 키와 혼동하지 않음 |

다음 작업에서 비밀 값 없는 `.env.example`과 시작 시 필수 변수 검증을 추가하면 재설정 시간을 줄일 수 있다. 어떤 파일이 우선 적용되는지도 실제 Next 실행 모드에 맞춰 확인한다.

### 제거와 업그레이드는 별도 판단

- Quill 관련 라이브러리·타입·유틸·mock, 중복 Markdown/HTML 처리 패키지, slider 등은 직접·간접 사용을 확인한 후 정리한다.
- `@types/next` 등 프레임워크 제공 타입과 겹치는 패키지, `install` 패키지의 필요성을 점검한다.
- Next/ESLint 설정, Storybook addons, Jest/@types 버전을 정렬한다. Prisma는 MongoDB 지원 여부를 먼저 확인한다.
- 서버 전용 data/DB/auth 모듈에 클라이언트 import가 섞이지 않도록 경계를 명시한다.
- 변경 전후에는 빌드뿐 아니라 로그인·글 저장·이미지 업로드와 기존 글 렌더링을 확인한다.

## 14. 유지·교체 의사결정 요약

| 분류 | 대상 | 이유 / 재검토 조건 |
| --- | --- | --- |
| 유지 | Next.js, React, TypeScript, CSS Modules | 현재 요구를 충족하며 재작성보다 수정 효과가 큼 |
| 유지하며 보완 | NextAuth, Markdown, Vercel, Prisma 6 + MongoDB | 권한·HTML 정책·운영·호환성 개선을 우선 |
| 우선 설계 재검토 | Firebase Storage 업로드 권한 | NextAuth와 분리된 인증 경계를 명확히 해야 함 |
| 조건부 교체 | MongoDB → PostgreSQL | 관계·집계·변경 관리 복잡도가 이전 비용보다 커질 때 |
| 조건부 단순화 | Jest/Vitest, 분석 도구, 중복 렌더러 | 중복 운영 비용이 실제로 발생할 때 |
| 방향 변경 시 재설계 | 정적 Markdown/MDX 또는 외부 CMS | 직접 만든 작성·관리 기능을 유지할 필요가 없어질 때 |

**1인 개발의 효율은 라이브러리가 적다는 뜻만은 아니다. 직접 구현할 필요가 적은 인증·파일·댓글·배포를 위임하고, 서비스 경계가 추가될 때의 연결 비용까지 관리하는 것이 핵심이다.** 현재 스택은 이 방향으로 설명할 수 있지만, Firebase 인증 경계와 비어 있는 테스트 실행 경로는 그 효율을 약화시키므로 먼저 보완한다.
