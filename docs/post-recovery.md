# 게시글 작성 내용 자동 복구

## 기존 문제

게시글을 작성하다가 실수로 뒤로 가거나 새로고침하면, 아직 서버에 저장하지 않은 제목과 본문이 유실되는 경우가 있었다. 작성 내용은 React 상태로만 관리되어 작성 화면을 벗어나거나 페이지가 다시 로드되면 복구할 수 없었다.

이를 해결하기 위해 작성 상태를 브라우저에 자동 보관하고, 작성 화면에 다시 들어오면 복원하는 `postRecovery` 기능을 추가했다. 사용자가 별도 저장 버튼을 누르지 않아도 마지막으로 보관된 내용부터 이어 쓸 수 있도록 하는 것이 목적이다.

## 초안 저장과의 구분

`postRecovery`는 실수로 화면을 벗어났을 때 작성 내용을 복구하기 위한 기능이다. 서버에 글을 저장해 나중에 다른 기기에서도 이어 쓰는 초안 저장과 구분한다.

| 구분                   | 자동 복구                      | 서버 초안 저장                           |
| ---------------------- | ------------------------------ | ---------------------------------------- |
| 코드에서 사용하는 이름 | `postRecovery`                 | `draft`                                  |
| 주된 목적              | 작성 중 내용 유실 방지         | 작성 중인 글을 보관하고 나중에 이어 쓰기 |
| 저장 위치              | 현재 브라우저의 `localStorage` | 서버                                     |
| 기기 간 공유           | 지원하지 않음                  | 서버 초안 기능에서 처리                  |

이 문서는 자동 복구의 현재 구현을 다룬다.

## localStorage를 선택한 이유

페이지를 다시 로드해도 남는 브라우저 저장소가 필요했다. `localStorage`는 탭이나 브라우저를 닫아도 데이터가 유지되므로, 같은 브라우저에서 작성 화면을 다시 열었을 때 내용을 복구할 수 있다.

입력할 때마다 서버에 요청하지 않고 브라우저에서 보관한다. 별도 API나 DB 모델을 추가하지 않고 기존 작성 화면에 적용할 수 있다는 점도 선택 이유다.

## 보관하는 데이터

제목과 본문뿐 아니라 작성 맥락을 복원하는 데 필요한 게시 설정도 함께 보관한다.

| 필드             | 내용                           |
| ---------------- | ------------------------------ |
| `title`          | 제목                           |
| `value`          | 마크다운 본문                  |
| `uploadedImages` | 업로드한 사진 URL 목록         |
| `thumbnailImg`   | 선택한 썸네일 URL              |
| `catSlug`        | 선택한 카테고리                |
| `tags`           | 선택한 태그                    |
| `isPublished`    | 공개 설정                      |
| `tagInput`       | 아직 추가하지 않은 태그 입력값 |

사진 파일 자체는 Firebase Storage에 업로드되며, 복구 데이터에는 URL만 포함된다. 복구는 사진을 다시 업로드하지 않는다.

저장 데이터는 `version`, `savedAt`, `content`로 구성한다. `version`은 데이터 형식의 버전을 나타내고, `savedAt`은 보관 시각을 기록한다. 현재 보관 시각으로 만료 여부나 서버 글과의 최신 여부를 판단하지는 않는다.

저장소 키는 다음과 같이 계정과 작성 대상을 구분한다.

```text
새 글: blog:post-recovery:v1:{사용자 이메일}:new
수정: blog:post-recovery:v1:{사용자 이메일}:edit:{게시글 slug}
```

이메일이 없으면 계정 구분 값으로 `local`을 사용한다. 계정마다 새 글 복구본은 하나이며, 수정 복구본은 게시글별로 보관한다.

## 동작 흐름

1. 로그인된 사용자가 작성 화면에 들어오면 초기 상태를 준비한다. 수정 화면에서는 서버에서 게시글 조회가 끝날 때까지 기다린다.
2. 해당 계정과 작성 대상의 저장소 키로 복구 데이터를 읽는다. JSON 파싱 후 Zod의 `postRecoverySchema.safeParse`로 데이터 구조를 검증한다.
3. 유효한 복구본이 있으면 제목·본문·게시 설정에 적용한다. 복구 여부를 묻는 별도 확인창 없이 자동으로 복원한다.
4. 화면 하단에 “작성 중이던 내용을 복구했습니다.” 토스트를 표시한다. 토스트는 4초 뒤 사라지며 직접 닫을 수도 있다.
5. 이후 작성 상태가 바뀌면 `useEffect`에서 JSON으로 직렬화하여 `localStorage`에 보관한다. 마지막으로 보관한 값과 같으면 중복 쓰기를 생략한다. 현재 지연 저장이나 주기 저장을 사용하지 않는다.
6. 모든 값을 최초 상태로 되돌리면 해당 복구본을 삭제한다.
7. 게시글 생성·수정 요청이 성공하면 복구본을 삭제하고 게시글 화면으로 이동한다. 요청이 실패하면 작성 상태와 복구본을 유지한다.

초기화 완료 여부를 `postRecoveryReady`로 관리하여, 복구 데이터를 읽기 전에 빈 작성 상태가 기존 복구본을 덮어쓰는 것을 방지한다. 수정 글도 서버 조회 이후 복구본을 적용하므로 조회 결과가 복구 내용을 덮어쓰지 않도록 한다.

`baseline`은 복구본을 적용하기 전 최초 상태를, `lastPersisted`는 마지막 보관 상태를 비교하는 데 사용한다. `savedSuccessfully`는 서버 저장 성공 뒤 복구본이 다시 생성되거나 불필요한 이탈 경고가 나타나는 것을 막는다.

## 화면 이탈과 오류 처리

서버에 반영하지 않은 변경이 있으면 `beforeunload` 이벤트를 등록해 새로고침·탭 닫기 시 브라우저의 기본 이탈 확인창을 요청한다. 경고 표시 여부와 문구는 브라우저 정책을 따른다. 사이트 내부 링크 이동이나 뒤로가기 전체를 차단하는 라우팅 가드는 구현하지 않았다. 화면을 벗어나더라도 보관이 완료된 데이터는 작성 화면을 다시 열 때 복구한다.

저장 데이터가 손상되었거나 스키마에 맞지 않으면 복구하지 않고 안내를 표시한다. 저장 공간 부족이나 브라우저 설정으로 보관이 실패해도 현재 입력 내용은 화면에 유지하고 실패 안내를 표시한다. 서버 저장 성공 후 복구본 삭제가 실패한 경우에는 게시글 이동을 계속하며, 이때 기존 복구본이 남을 수 있다.

초기에 사용한 `blog:post-draft:` 키도 읽을 수 있도록 호환 처리를 두었다. 새 키에 데이터가 없으면 이전 키를 읽고, 유효한 데이터를 새 `blog:post-recovery:` 키로 옮긴 뒤 이전 키를 삭제한다.

## 범위와 제한

복구본은 같은 사이트의 같은 브라우저 프로필에서만 사용할 수 있다. 브라우저 데이터를 삭제하거나 시크릿 모드를 종료하면 사라질 수 있으며, 서버 백업이나 기기 간 동기화를 제공하지 않는다. 로그아웃할 때 복구본을 삭제하거나 별도 암호화하는 동작도 없다.

같은 계정으로 동일한 작성 대상을 여러 탭에서 열면 같은 키를 사용하므로 마지막으로 보관된 값이 남는다. 탭 간 변경 동기화나 충돌 감지는 지원하지 않는다. 서버 글이 변경된 뒤에도 저장소에 유효한 복구본이 남아 있으면 그 복구본을 우선 적용한다.
