# API 응답 타입 기준

`src/types/api`의 응답 타입은 HTTP로 제공하는 필드를 명시한다. Prisma 모델을 바꿔도 API 응답 계약이 자동으로 늘어나지 않는다. 요청 타입도 이 디렉터리에서 관리한다.

`src/lib/serializers/responses.ts`는 Prisma 조회 결과에서 계약에 포함된 필드만 골라 응답으로 변환한다. 카테고리와 태그의 서버 렌더링 데이터도 같은 필드 선택을 거친다. 게시글은 서버 렌더링에서 `Date`를 유지하는 `PostView`를 사용하고, JSON 응답에서는 날짜를 ISO 문자열로 변환한다.

예를 들어 새로운 DB 필드를 추가할 때 API에 노출하려면 응답 타입과 변환 함수, 관련 테스트를 함께 수정한다. 반대로 화면에서 응답 일부만 필요하면 `Pick` 등으로 응답 타입에서 필요한 부분을 파생할 수 있다.

게시글 응답과 서버 렌더링 데이터에서는 작성자 이메일과 이메일 인증일을 제외한다. 상세 화면의 작성자 여부는 서버에서 세션을 확인해 계산하며, 수정·삭제 API는 요청마다 별도로 권한을 검사한다. 태그 상세는 공개 게시글만 조회하는 기존 정책을 유지한다.

게시글·카테고리·태그의 요청 본문은 서버에서 Zod로 검증한다. 클라이언트 서비스는 `parseApiResponse`로 실제 사용하는 주요 성공 응답을 `src/lib/zod`의 도메인별 스키마로 검증하고, 검증된 데이터만 React Query에 전달한다. 응답 타입은 스키마에서 `z.infer`로 파생한다. 목록·상세 등 클라이언트 서비스가 현재 사용하지 않는 응답 스키마도 타입 계약을 정의하지만, 런타임에 자동 검증되는 것은 아니다.

오류 응답은 `message`가 문자열인지 확인하고, 형식이 다르거나 JSON을 읽지 못하면 요청별 기본 오류를 사용한다. 태그 생성의 409 응답은 기존 태그 형식과 일반 오류를 구분한다. 게시글 수정·삭제와 카테고리·태그 삭제처럼 성공 응답 본문을 사용하지 않는 서비스는 성공 여부만 확인한다. 이미 서버 변경이 완료된 뒤 사용하지 않는 본문 검증에 실패해 작업 전체가 실패한 것처럼 표시하는 상황을 피하기 위해서다.

응답 검증 실패는 응답 계약이 맞지 않는다는 뜻이며, 생성 요청에서 검증이 실패했더라도 서버에 데이터가 이미 저장됐을 수 있다. 이 경우 다시 시도하기 전에 실제 저장 여부를 확인해야 한다. 외부 서비스의 모든 응답이나 HTTP 경로·쿼리 파라미터까지 검증하는 것은 아니다.
